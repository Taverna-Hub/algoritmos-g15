# Relatório do Projeto

Este projeto consiste em um sistema embarcado e web para monitoramento de presença em um ambiente, combinando duas formas complementares de detecção: a identificação passiva de dispositivos WiFi próximos e a contagem de movimentos de entrada e saída por meio de um sensor óptico. A proposta geral é capturar sinais do ambiente físico, transportar esses dados por MQTT, processá-los em serviços intermediários, persistir as informações em banco de dados e disponibilizar os resultados em uma API e em um painel web.

O sistema foi pensado como uma arquitetura distribuída, em que cada parte tem uma responsabilidade específica. Os dispositivos embarcados fazem a coleta dos dados no ambiente. O broker MQTT e o Node-RED fazem a comunicação e a orquestração das mensagens. Os notebooks em Python processam os dados recebidos e gravam os resultados no banco. O backend expõe esses dados por meio de uma API REST. O frontend consome essa API e apresenta as informações de forma visual para o usuário.

O fluxo principal do detector de dispositivos WiFi funciona a partir de um ESP32 configurado para capturar pacotes WiFi de forma passiva. Isso significa que o sistema não precisa que os celulares, notebooks ou outros equipamentos se conectem diretamente a uma rede controlada pelo projeto. Em vez disso, o ESP32 observa pacotes transmitidos no ambiente, como quadros de gerenciamento, probe requests, beacons e outros sinais emitidos por dispositivos próximos. A partir desses pacotes, são extraídas informações como endereço MAC, intensidade do sinal RSSI, canal, frequência, tipo de frame e quantidade de vezes que aquele dispositivo apareceu em uma janela de captura.

Esses dados coletados pelo ESP32 são enviados para o broker MQTT Mosquitto no tópico `esp32/wifi/scan`. O MQTT foi escolhido por ser um protocolo leve, muito usado em aplicações de Internet das Coisas, sistemas embarcados e comunicação entre dispositivos com poucos recursos. Ele permite que o hardware publique mensagens sem precisar conhecer diretamente todos os consumidores desses dados. O broker recebe as mensagens e distribui para os serviços interessados.

O Node-RED atua como uma camada de orquestração e validação das mensagens. Ele recebe o payload bruto publicado pelo ESP32, faz o parse do JSON, valida se a estrutura está correta, verifica se os endereços MAC são válidos, normaliza campos como MAC address, RSSI, canal e frequência, e então publica uma mensagem padronizada no tópico `nodered/wifi/data`. Essa etapa é importante porque separa o dado bruto vindo do hardware do dado já tratado que será consumido pelo processamento em Python.

O processamento dos dados WiFi é feito pelo módulo `ML`, implementado como um serviço de notebook em Python. Esse serviço assina o tópico `nodered/wifi/data`, recebe os dispositivos detectados e realiza uma análise sobre cada registro. Entre as funções principais estão a identificação do fabricante ou possível tipo de dispositivo a partir do OUI do endereço MAC, a estimativa de distância com base no RSSI e na frequência, e a classificação simples da localização como mais próxima ou mais distante. O cálculo de distância usa um modelo simplificado de perda de percurso, considerando a potência do sinal recebido e um coeficiente de propagação.

Embora o projeto use o termo Machine Learning, a implementação atual funciona principalmente como uma camada de análise e enriquecimento de dados. Ela aplica regras, lookup de fabricantes e fórmulas de estimativa para transformar capturas de baixo nível em informações mais úteis para visualização e tomada de decisão. Essa abordagem deixa o projeto preparado para evoluir futuramente para modelos reais de ML, como classificação de tipo de dispositivo, reconhecimento de padrões temporais, análise de aglomeração e estimativas de presença mais sofisticadas.

Além do detector WiFi, o projeto possui um segundo hardware, localizado em `hardware_secondary`, responsável pela detecção de movimento com sensores ópticos. Esse módulo usa um ESP8266 com dois sensores posicionados em sequência. A lógica básica é identificar a ordem em que os sensores são ativados. Quando o sensor A é ativado antes do sensor B, o sistema interpreta como uma entrada. Quando o sensor B é ativado antes do sensor A, o sistema interpreta como uma saída. Essa lógica permite estimar a direção do movimento de uma pessoa passando pelo ponto monitorado.

Esse sensor óptico complementa a detecção WiFi porque fornece uma contagem física de entrada e saída, enquanto o WiFi fornece uma percepção indireta da presença por dispositivos próximos. A detecção WiFi pode indicar quantos aparelhos estão no ambiente, mas nem sempre corresponde exatamente ao número de pessoas, pois uma pessoa pode carregar mais de um dispositivo ou nenhum dispositivo. Já o sensor óptico observa o movimento físico, permitindo manter uma variável de contagem de pessoas associada ao sensor 2.

Quando o ESP8266 detecta um evento de entrada ou saída, ele publica uma mensagem MQTT no tópico `esp8266/event`. O payload contém o identificador do dispositivo, o tipo de evento e um timestamp aproximado. O Node-RED recebe essa mensagem, valida se o evento é `entrada` ou `saida`, e republica o dado normalizado no tópico `nodered/esp8266/event`. A partir desse ponto, um notebook específico, `notebook_sensor_optic.py`, assina esse tópico e atualiza a contagem de pessoas do sensor óptico.

No caso do sensor óptico, a regra de negócio é direta: cada evento de `entrada` incrementa a contagem em 1, e cada evento de `saida` decrementa a contagem em 1. Para evitar valores sem sentido, a contagem não fica negativa; se uma saída for recebida quando a contagem já estiver em zero, o valor permanece zero. Esse comportamento protege o sistema contra leituras incompletas, ruído no sensor ou eventos fora de ordem.

O backend do projeto foi desenvolvido em FastAPI. Ele não consome MQTT diretamente; essa responsabilidade fica nos notebooks/processadores. O backend trabalha sobre os dados já persistidos no banco PostgreSQL. Essa divisão deixa a API mais simples e estável, porque ela não precisa manter conexão com o broker nem lidar diretamente com eventos em tempo real. Sua responsabilidade principal é disponibilizar endpoints REST para consulta de dispositivos detectados, histórico de detecções, estatísticas e contagem do sensor óptico.

O banco de dados PostgreSQL armazena diferentes tipos de informação. A tabela de dispositivos mantém um registro único por MAC address, com dados como primeira e última detecção, RSSI, frequência, canal, tipo de frame, quantidade de aparições, SSID, fabricante ou sistema identificado e distância estimada. A tabela de detecções registra o histórico de capturas ao longo do tempo. A tabela de análise guarda os resultados derivados do processamento. Para o sensor óptico, foi adicionada uma estrutura de contador de sensor, armazenando o `sensor_id`, a quantidade atual de pessoas e a data da última atualização.

O frontend foi desenvolvido com React e Vite. Ele consome a API do backend para exibir um dashboard com indicadores e listas de dispositivos. O painel apresenta informações como dispositivos detectados no lote atual, marca ou fabricante mais comum, estimativa de pessoas por WiFi e a contagem física do sensor óptico 2. Essa separação é importante porque mostra duas perspectivas diferentes do mesmo ambiente: uma baseada em radiofrequência e outra baseada em passagem física.

Do ponto de vista de tecnologias, o projeto combina C/C++ em sistemas embarcados, MQTT para comunicação, Node-RED para orquestração visual de fluxos, Python para processamento e integração com banco, FastAPI para construção da API, SQLAlchemy para modelagem e acesso ao banco de dados, PostgreSQL para persistência, React para interface web e Docker Compose para execução dos serviços de infraestrutura como Mosquitto, Node-RED e PostgreSQL.

O detector de dispositivos WiFi é útil para observar presença tecnológica no ambiente. Ele permite perceber quais dispositivos estão próximos, com que intensidade de sinal aparecem, em quais canais são detectados e com que frequência surgem nas capturas. A partir desses dados, o sistema consegue montar uma visão aproximada de ocupação, movimentação e permanência de equipamentos no local. Esse tipo de abordagem pode ser aplicado em estudos de fluxo de pessoas, monitoramento de ambientes, análise de presença em salas, laboratórios, eventos ou espaços compartilhados.

O sensor óptico de movimento, por sua vez, atua como uma medição mais objetiva de fluxo físico. Ele não identifica quem passou nem qual dispositivo a pessoa carrega, mas indica a direção do movimento. Com dois sensores em sequência, é possível inferir entrada e saída a partir da ordem de ativação. Essa informação é especialmente útil para manter uma contagem corrente de pessoas em um ambiente, desde que o ponto de passagem seja bem definido e o posicionamento dos sensores reduza leituras ambíguas.

A combinação das duas técnicas torna o projeto mais interessante do que o uso isolado de apenas uma delas. A detecção WiFi fornece informações ricas sobre dispositivos e presença digital, enquanto o sensor óptico fornece uma contagem física baseada em movimento. Em conjunto, essas fontes permitem comparar a quantidade de dispositivos próximos com a quantidade de entradas e saídas detectadas, ajudando a validar hipóteses sobre ocupação e comportamento no ambiente.

Em termos de comunicação, o uso de MQTT facilita a integração entre os hardwares e os serviços de software. Cada dispositivo publica eventos em tópicos específicos, e os consumidores assinam apenas os tópicos de interesse. Isso permite adicionar novos sensores ou novos processadores sem modificar toda a arquitetura. O Node-RED funciona como uma camada intermediária importante porque padroniza, filtra e redireciona as mensagens, reduzindo o acoplamento entre hardware e aplicação.

O projeto também adota uma separação clara entre ingestão, processamento, persistência e visualização. A ingestão acontece nos hardwares e no broker MQTT. O processamento acontece no Node-RED e nos notebooks Python. A persistência fica no PostgreSQL. A consulta é feita pelo backend FastAPI. A visualização é feita pelo frontend React. Essa divisão facilita manutenção, testes e evolução do sistema, pois cada parte pode ser ajustada com impacto limitado nas demais.

Existem alguns desafios técnicos naturais nesse tipo de projeto. No detector WiFi, a leitura passiva de dispositivos depende do comportamento dos aparelhos, do canal monitorado, da intensidade do sinal e das políticas modernas de privacidade, como randomização de MAC address. No sensor óptico, a precisão depende do posicionamento físico, do intervalo entre sensores, do tempo limite para considerar um movimento completo e da filtragem de ruído. Na comunicação MQTT, é necessário garantir que o broker esteja acessível, que os tópicos estejam corretos e que o firmware implemente corretamente o protocolo de conexão e publicação.

Como evolução futura, o sistema pode incluir autenticação e TLS no MQTT, tratamento mais robusto de eventos duplicados, calibração dos sensores ópticos, histórico de entradas e saídas, reset manual da contagem, associação entre horários de detecção WiFi e eventos físicos, modelos mais avançados de estimativa de distância, dashboards temporais e alertas baseados em ocupação. Também seria possível expandir o projeto para múltiplos sensores ópticos e múltiplos ESP32 de captura WiFi, permitindo monitorar diferentes pontos de um ambiente.

Em resumo, o projeto é uma solução integrada de monitoramento de presença que une IoT, redes sem fio, mensageria, processamento de dados, backend web e interface de visualização. O detector de dispositivos mostra a presença digital por meio de sinais WiFi, enquanto o sensor óptico registra movimentos físicos de entrada e saída. A arquitetura baseada em MQTT, Node-RED, notebooks Python, PostgreSQL, FastAPI e React permite transformar eventos brutos do ambiente em dados persistidos, consultáveis e visualmente compreensíveis.
